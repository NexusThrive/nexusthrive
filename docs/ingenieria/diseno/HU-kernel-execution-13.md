# Diseño: HU-kernel-execution-13

## Resumen
Se crea `kernel/execution`: un motor que abre la transacción con el espacio fijado (`state.InSpace`), verifica con `Authorizer.Check` antes de cualquier escritura y entrega a la operación una `Tx` que expone solo primitivas de estado, estampando actor y `request_id` desde la llamada. Sin migración (la siguiente libre, 00014, queda sin usar): el motor es código. Estado: lista, sin bloqueos; exige el ADR-0035 antes del código. La nota supera las 150 líneas por la lista de ataques y pruebas (como commitments-11 y timers-12).

## Tipo de trabajo
`backend`: Go del kernel y pruebas; sin contrato público ni app.

## Módulos a tocar
- `kernel/capability/authorizer.go`: accesores `Catalog() model.Catalog` y `Clock() model.Clock`. El motor toma catálogo y reloj del Authorizer: una sola inyección, sin divergencia entre el reloj que verifica y el que reclama o dispara.
- `kernel/state/exchange.go`, `commitment.go`, `timer.go`: las variantes `Append*` pasan de `validateExchangeActor` (solo `system`, un sustituto del permiso) a `validateWriteActor` (tipo conocido y participante UUID no nulo), porque el criterio 1 escribe como persona y el permiso ya lo decide `Check`. Los envoltorios con pool (`RecordExchange`, `CreateCommitment`, `CancelCommitment`...) conservan `validateExchangeActor` (solo `system`; son para pruebas y arranque) y lo llaman antes de abrir la transacción. `FireDueTimersTx` mantiene `validateFire` (solo `system`: defensa adicional a `kernel.timer.process`). Los doc comments de `ClaimOutbox`, `FireDueTimers` y los envoltorios dicen "uso autónomo y pruebas; producción pasa por `execution.Engine`".
- `kernel/state/role.go` (`translateGrantError`): `23001` a `permission_denied` (seguimiento 50, mismo precedente que `translateSpaceError`).
- `kernel/state/transaction.go` o `exchange.go`: nueva `TranslateCommitError(err error) error`, exportada (ver Contrato).
- `kernel/architecture_test.go`: regla de importadores de `kernel/state` (ver Pruebas).
- Pruebas de `state` que afirman `permission_denied` para una persona vía `Append*` (buscar `only the system actor`): pasan al envoltorio con pool; las de `Append*` ahora afirman éxito con persona y `permission_denied` con actor nulo o sin participante.
- Docs: `docs/02-arquitectura/kernel.md` (sección "Motor de ejecución"; quitar las menciones "queda para execution-13" de permisos y timers; aclarar el paso 2 del camino: la identidad la resuelve la puerta y el permiso se verifica dentro de la transacción del motor, ADR-0032), `docs/02-arquitectura/contrato.md` (operación declarada en Go con lista de permisos), `docs/05-decisiones/README.md`, `kernel/README.md`, backlog (estado), `docs/ingenieria/sprint-01/seguimientos.md` (ver Riesgos, tabla de seguimientos).

## Cambios de datos
Ninguno. No hay tablas, privilegios ni migración. `request_id` vive solo en `kernel.events` (y `access_audit`, B4): el outbox cuelga del evento por `event_seq`.

## Contrato
```go
package execution
type Operation struct {
    Name        string       // dotted lowercase, namespace = first segment; "kernel" reserved to built-ins
    Permissions []string     // every key is verified; at least one, all in the catalog
    Capability  string       // optional; must be active in the space
    Risk        model.Risk   // must equal the highest risk among Permissions
    Idempotent  bool         // declared support; required when Risk is money
}
type Call struct{ Actor model.Actor; SpaceID, RequestID string } // idempotency-14 adds IdempotencyKey here: Run keeps its signature
type Handler func(ctx context.Context, tx *Tx) error
func NewEngine(pool *sql.DB, auth *capability.Authorizer, ops ...Operation) (*Engine, error) // validates ALL, registers built-ins
func (e *Engine) Run(ctx context.Context, call Call, name string, fn Handler) error
func (e *Engine) FireDueTimers(ctx context.Context, call Call, limit int) (model.TimerRun, error)           // kernel.timer.fire, kernel.timer.process
func (e *Engine) ClaimOutbox(ctx context.Context, call Call, s model.Subscriber, limit int) ([]model.OutboxRow, error) // kernel.outbox.claim, kernel.outbox.claim
func NewRequestID() string // UUID v7, for internal callers with no request
type PanicError struct{ Operation string; Value any; Stack []byte } // Error() has operation and value, no stack; no Unwrap
// Tx is valid only inside the handler. It holds the verified actor, the space and the request id.
func (t *Tx) SpaceID() string; func (t *Tx) Actor() model.Actor; func (t *Tx) RequestID() string
func (t *Tx) RecordExchange(ctx, model.NewExchange) (model.Exchange, error)        // needs kernel.exchange.write declared
func (t *Tx) CreateCommitment(ctx, model.NewCommitment) (model.Commitment, error)  // needs kernel.commitment.write declared
func (t *Tx) AppendEvent(ctx, EventInput, ...model.Subscriber) (model.Event, error) // write or money operations only
func (t *Tx) ReadEvents(ctx, fromSeq int64, limit int) ([]model.Event, error)      // needs kernel.event.read declared
type EventInput struct{ Type string; Version int; SubjectRef string; Payload json.RawMessage; OccurredAt time.Time } // no Actor, no RequestID
func state.TranslateCommitError(err error) error // known deferred constraints (exchanges_conservation, exchanges_min_entries, timers_coherent, ...) to rule_violation; the rest untouched
```
**Orden de `Run`** (cada paso corta): (1) validar `Call` antes de abrir nada: `RequestID` con `^[A-Za-z0-9._:-]{1,128}$` (invalid_input; sin ese filtro un valor con saltos de línea entra a registros), `fn` no nulo, operación registrada (si no, invalid_input), `SpaceID` UUID no nulo (lo valida `InSpace`); (2) `defer recover` externo que convierte un pánico en `*PanicError` (el rollback ya ocurrió: la defer de `inTransaction` corre antes mientras el pánico desenrolla); (3) `state.InSpace`; (4) dentro: para `read`, `SET TRANSACTION READ ONLY` (defensa en profundidad: el rol de la API no impide escribir en una lectura); (5) `Authorizer.Check` por cada clave de `Permissions`, con `Capability` en la primera, todo antes de construir la `Tx`; (6) `fn(ctx, tx)`; (7) cerrar la `Tx` (`closed = true`, también si `fn` devolvió error) y confirmar. Una `Tx` capturada y usada después devuelve `rule_violation`, sin pánico.
**Reglas de `Tx`:** sin SQL crudo ni `*sql.Tx` (solo las pruebas internas lo ven). Cada método exige que su permiso esté en `Permissions` (una operación que declaró solo `commitment.write` no escribe intercambios: `permission_denied` sin escritura). Actor y `request_id` se estampan desde `Call`: `EventInput` no los tiene, así un manejador no atribuye un evento a otro. `Type` de evento y `Kind` de intercambio o compromiso deben empezar con el espacio de nombres de la operación (`test.` para `test.exchange_and_commitment`): una operación de una extensión no puede falsificar `kernel.commitment.expired`, que exige la coherencia de timers (`rule_violation`). Un manejador que traga un error de base y devuelve nil no confirma: pgx devuelve `ErrTxCommitRollback` y se prueba.
**Registro (criterio 7):** `NewEngine` falla con `invalid_input` si: nombre no válido o duplicado o con prefijo `kernel.`; sin permisos, repetidos o fuera del catálogo; `Risk` distinto del mayor riesgo de las claves (una operación `money` no se declara `write` para esquivar); capacidad mal formada; `Risk` `money` con `Idempotent` falso. Declarar no es implementar: hasta idempotency-14 la barrera real de una operación de dinero es `exchanges_idempotency_key` (única por espacio).
**Clasificación de errores** (`errors.go`, en este orden): tipado pasa sin envolver; `*PanicError` pasa; errores de contexto se envuelven sin tipar; `23001` a `permission_denied`; fallos de `COMMIT` por `TranslateCommitError`; `42501` y `40001`/`40P01` se envuelven SIN tipar (un privilegio faltante nunca se disfraza de `rule_violation` o `not_found`; no hay reintento: el contrato no tiene código reintentable y reejecutar `fn` repite efectos); el resto, `fmt.Errorf("execute %s: %w", name, err)`.
**Operaciones del kernel** (`builtin.go`; sus manejadores usan métodos no exportados de `Tx`, inalcanzables desde fuera): `kernel.timer.fire` (`kernel.timer.process`, `write`) llama `FireDueTimersTx`; `kernel.outbox.claim` (`kernel.outbox.claim`, `write`) llama `ClaimOutboxTx`. Por ser `write`, un espacio suspendido las pausa (`space_suspended`).

Ayudantes de `laws` (`kernelTables`, `rowCounts`, `diff`, `clock`) se reutilizan; las tablas salen del catálogo de la base. ## Riesgos técnicos y mitigación
- **Contradicciones y recomendaciones.** (1) Criterio 1 ("las cuatro escrituras con el mismo `request_id`") contra `modelo-de-datos/kernel.md` y la regla de la historia ("`request_id` común a evento y acceso privilegiado"): `exchanges` y `commitments` no tienen la columna. Recomendación: sin migración; el `request_id` vive en el evento, el outbox cuelga de él y el `payload` nombra intercambio y compromiso. Alternativa descartada: columna en dos tablas con triggers de inmutabilidad y privilegios por columna, que rehace pruebas de 00009 y 00012 por una trazabilidad que el evento ya da. El responsable puede reformular el criterio. (2) `Check` recibe una sola clave y el criterio 1 pide dos: `Operation.Permissions` es lista. (3) `AppendExchange` exige actor `system`, que contradice el criterio 1: se relaja en `Append*` (ver Módulos). (4) `kernel.md` lista la idempotencia en el paso 4 del motor: aquí solo se declara (idempotency-14). (5) El contrato no tiene código "interno" para el criterio 10: el pánico es un `*PanicError` sin tipo y B3 lo traduce a 500 sin mensaje. (6) `Check` devuelve `space_suspended` también para `closed` (ADR-0032).
- **Ruta alternativa (decisión).** El motor es código: quien tenga el pool con el rol de la API puede usar `state.*` o SQL crudo y saltarse `Check`; la base solo impide lo que sus disparadores y RLS impiden. Aceptable en M1: el único proceso con el pool es el kernel. Mitigación: `Tx` sin SQL, pool no exportado, prueba de importadores. Precondición de B3 (ADR-0035): las puertas y extensiones reciben solo `Engine`; nunca el pool ni `state`; el `Actor` se construye solo desde un token validado y `ActorSystem` nunca desde una petición (seguimientos 28, 29, 46); `MarkOutboxSent`/`MarkOutboxFailed` no se exponen (seguimiento 42).
- **`SET LOCAL` y conexiones.** `set_config(..., true)` y `SET TRANSACTION` mueren con la transacción; un pánico o error pasa por el `Rollback` diferido. La prueba con una sola conexión lo demuestra.
- **Seguimientos.** Entran: 20 (cableado de extremo a extremo de `Check`), 42 y 49 y 62 (`timer.process` y `outbox.claim`), 44 (pausa por suspensión), 45 (permiso aplicado; el CHECK sobre `claimed_until` se difiere a B3 por su dependencia del reloj), 50 (`23001`), 29 y 28 (límite documentado, B3 lo cierra). Se difieren: 23 (revocar al vencer: sin operación de grants en el motor todavía), 33 (`40001`: falta código reintentable; ADR-0004), 58 (`NULL` en SQL es un no-op sin efecto; una migración que reemplace `guard_commitment_update` no vale el riesgo: prueba de fijación en `laws-15`), 60 (reprogramar no es alcanzable por el motor: el evento `kernel.commitment.rescheduled` llega con la primera operación que lo exponga). Los demás no cambian.
- **Concurrencia.** `Check` bloquea con `FOR SHARE` hasta el final: una revocación espera. Sin reintentos automáticos.
- **Leyes.** Conservación (C4), memoria (C1 a C3: evento con actor y `request_id`, nada a medias), compromiso (C1: el timer nace con él), permiso (C5, C6, C9 y operaciones del kernel), movimiento (reloj del Authorizer, `kernel.timer.fire`). `laws-15` cierra con la matriz de cinco leyes sobre todas las operaciones, las pruebas diferidas (58, 65, 67) y la enmienda de ADR-0027.
