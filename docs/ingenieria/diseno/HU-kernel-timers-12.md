# Diseño: HU-kernel-timers-12

## Resumen
Migración `00013_timers.sql`: `kernel.timers` 1:1 con el compromiso, creado y reprogramado por disparadores (valen para todo escritor) y cancelado cuando el compromiso se cierra. Un compromiso solo llega a `expired` al disparar su timer vencido según el reloj de la base, y `state.FireDueTimers` hace en una transacción el disparo, el evento `kernel.commitment.expired` v1 y su fila de outbox `internal`. Estado: lista, sin bloqueos; requiere el ADR-0034 antes del código. La nota supera las 150 líneas por la exigencia de SQL, ataques y pruebas (como commitments-11).

## Cambios de datos
Decisiones. (b) El timer lo crea un disparador `AFTER INSERT` en `commitments`, no Go: vale para el rol de la API, el administrador y execution-13 (que solo envuelve la transacción) y no hay cómo olvidarlo. El disparador no puede generar UUID v7 (A4), así que el id del timer es el id del compromiso (ya v7; un solo timer de vencimiento por compromiso, reprogramado en sitio; recordatorios futuros usarán ids propios). `due_at` se reprograma con `UPDATE (due_at)` y un disparador mueve `fire_at`. (c) Cerrar el compromiso cancela el timer en un disparador, igual para SQL directo. (d) `expired` no se concede como escritura libre: se llega solo por cascada del timer. Toda comprobación de tiempo usa `now()` de la base (la transacción), nunca un valor del llamador: el reloj inyectable solo puede ir por detrás del reloj real (techo). Así `expired` ocurre únicamente con `due_at <= now()` aunque el llamador mienta, y se resuelve el seguimiento 53.
```sql
CREATE TABLE kernel.timers (
  id uuid PRIMARY KEY CHECK (substr(id::text, 15, 1) = '7'),
  space_id uuid NOT NULL REFERENCES kernel.spaces (id),
  commitment_id uuid NOT NULL,
  fire_at timestamptz NOT NULL,
  status text NOT NULL DEFAULT 'scheduled' CONSTRAINT timers_status_check CHECK (status IN ('scheduled','fired','canceled')),
  fired_at timestamptz,                               -- stamped by trigger, never in a grant
  created_at timestamptz NOT NULL DEFAULT now(),      -- stamped by trigger
  CONSTRAINT timers_fired_coherent CHECK ((status = 'fired') = (fired_at IS NOT NULL)),
  CONSTRAINT timers_fired_after_fire_at CHECK (fired_at IS NULL OR fired_at >= fire_at),
  CONSTRAINT timers_commitment_fkey FOREIGN KEY (commitment_id, space_id) REFERENCES kernel.commitments (id, space_id));
CREATE UNIQUE INDEX timers_one_scheduled_key ON kernel.timers (commitment_id) WHERE status = 'scheduled';
CREATE INDEX timers_due_idx ON kernel.timers (space_id, fire_at, id) WHERE status = 'scheduled';
-- RLS ENABLE + FORCE; policies select, insert, update with (SELECT kernel.current_space_id()); no delete policy.
GRANT SELECT ON kernel.timers TO nexusthrive_api;
GRANT INSERT (id, space_id, commitment_id, fire_at) ON kernel.timers TO nexusthrive_api;  -- the creation trigger runs as the invoker
GRANT UPDATE (status, fire_at) ON kernel.timers TO nexusthrive_api;                       -- fired_at, created_at: never
GRANT UPDATE (due_at, status) ON kernel.commitments TO nexusthrive_api;                   -- cascade runs as the invoker; both guarded
```
Funciones: `plpgsql`, `SET search_path = pg_catalog, pg_temp`, sin `SECURITY DEFINER`, objetos `kernel.x`, `ERRCODE` y `CONSTRAINT` como en 00012; un disparador por tabla y momento. Las guardas valen también para el dueño.
1. `timers_guard_insert` BEFORE INSERT: `status` distinto de `scheduled` o `fired_at` no nulo, `restrict_violation`; el compromiso (`FOR NO KEY UPDATE`) debe existir y estar `open`; `fire_at = due_at`; `created_at := now()`.
2. `timers_guard_update` BEFORE UPDATE: `OLD.status <> 'scheduled'` rechaza todo (terminales); `id`, `space_id`, `commitment_id`, `created_at` inmutables; `fired_at` escrito por el llamador se rechaza; un solo efecto. Bloquea el compromiso `FOR NO KEY UPDATE` y según el efecto: `fire_at` solo si el compromiso está `open` y `NEW.fire_at = due_at`; `status = 'fired'` solo si está `open` y `OLD.fire_at <= now()`, y fija `NEW.fired_at := now()`; `status = 'canceled'` solo si el compromiso NO está `open`; cualquier otro, rechazo.
3. `timers_expire_commitment` AFTER UPDATE `WHEN (OLD.status = 'scheduled' AND NEW.status = 'fired')`: `UPDATE kernel.commitments SET status = 'expired' WHERE id = NEW.commitment_id AND space_id = NEW.space_id AND status = 'open'`.
4. `commitments_timer_create` AFTER INSERT en `commitments`: `INSERT INTO kernel.timers (id, space_id, commitment_id, fire_at) VALUES (NEW.id, NEW.space_id, NEW.id, NEW.due_at)`.
5. `commitments_timer_sync` AFTER UPDATE `WHEN (OLD.due_at IS DISTINCT FROM NEW.due_at OR OLD.status IS DISTINCT FROM NEW.status)`: si cambió `due_at`, `UPDATE timers SET fire_at = NEW.due_at WHERE commitment_id = NEW.id AND status = 'scheduled'`; si el estado dejó de ser `open`, `UPDATE timers SET status = 'canceled' WHERE commitment_id = NEW.id AND status = 'scheduled'` (tras expirar no hay filas: la cascada termina).
6. `CREATE OR REPLACE kernel.guard_commitment_update()`: (i) quita `due_at` de la lista inmutable y lo cuenta como cuarto efecto; cambiarlo exige `NEW.due_at >= now()` (si no, `integrity_constraint_violation`, `CONSTRAINT 'commitments_reschedule_past'`), no toca `closed_at`; (ii) `status = 'expired'` exige `OLD.due_at <= now()` Y `EXISTS` un timer del compromiso con `status = 'fired' AND fired_at = now() AND fire_at <= now()` (es decir, disparado en esta transacción); si no, `restrict_violation`; el resto de la guarda no cambia (`closed_at := now()`, un efecto, terminales).
7. Segunda capa: `CONSTRAINT TRIGGER timers_coherence_check AFTER INSERT OR UPDATE` en `timers` y en `commitments`, `DEFERRABLE INITIALLY DEFERRED`, función `kernel.check_timer_coherence()` (lee con RLS: sin espacio actual no ve el compromiso y falla cerrado): compromiso `open` tiene exactamente un timer `scheduled` con `fire_at = due_at`; no `open` no tiene ninguno `scheduled`; si hay un timer `fired`, el compromiso es `expired` y existe un evento del espacio con `type = 'kernel.commitment.expired'`, `version = 1` y `subject_ref = 'kernel.commitment/' || id` (ley de memoria para todo escritor). Error `timers_coherent`.
8. `timers_no_delete` y `timers_no_truncate` con `kernel.reject_timer_removal()` (también en cascada).

Candidatos y bloqueo: `SELECT t.id::text, t.commitment_id::text FROM kernel.timers t JOIN kernel.commitments c ON c.id = t.commitment_id AND c.space_id = t.space_id WHERE t.space_id = kernel.current_space_id() AND t.status = 'scheduled' AND t.fire_at <= LEAST($1::timestamptz, now()) ORDER BY t.fire_at, t.id LIMIT $2 FOR NO KEY UPDATE OF c SKIP LOCKED`. ## Riesgos técnicos y mitigación
- **Contradicciones y recomendaciones.** 1) Historia, criterio 2, contra commitments-11 (`due_at` inmutable): se relaja en 00013 con guarda y grant. 2) "Reloj inyectable" contra el techo del reloj de la base: el reloj inyectado puede ir por detrás, no por delante; las pruebas usan fechas pasadas (`starts_at` es insertable). Alternativa descartada: aceptar cualquier reloj, que deja a quien tenga el rol de la API expirar cualquier compromiso. 3) El ER de `timers` lista `signal_type` y `payload`: no se crean (regla 11; recordatorios fuera de alcance). 4) La historia dice "reclamar": aquí es disparar en la misma transacción, sin arrendamiento ni `claim_token`. 5) `leyes.md` ("emite señales al vencer"): la señal es el evento `kernel.commitment.expired`. 6) Seguimiento 55: `due_at` pasado se admite al crear (necesario para probar) y vence en el primer disparo; reprogramar al pasado se rechaza, porque si no el rol de la API forzaría el vencimiento de cualquier compromiso.
- **Gancho de commitments-11 (seguimiento 53).** La API recibe `UPDATE (status)` en `commitments` solo porque la cascada corre con sus derechos; la guarda impide cualquier valor distinto de `expired`, y `expired` solo con timer disparado en la misma transacción, `fire_at <= now()` y `due_at <= now()`. Camino de ataque restante: quien tenga el rol de la API puede disparar timers realmente vencidos por SQL; es el proceso del kernel (seguimientos 42, 45) y el evento obligatorio al confirmar cierra el hueco de memoria.
- **Reprogramar no escribe evento** (la ley de memoria no cubre el cambio de `due_at`): seguimiento 60, decidir en execution-13 un `kernel.commitment.rescheduled`.
- **Interbloqueos.** Orden fijo compromiso y luego timer en el kernel; un escritor directo sobre `timers` puede dar 40P01, que el llamador reintenta. `SKIP LOCKED` hace que un compromiso ocupado se atienda en la siguiente ronda (seguimiento 61: sin garantía de latencia).
- **`now()` es el inicio de la transacción.** Una transacción larga ve un reloj atrasado: no dispara de más. El techo evita errores de sesgo entre aplicación y base.
- **Sin disparador efectivo si un administrador los deshabilita** (límite de ADR-0028); quedan `CHECK`, `UNIQUE`, FK compuesta e índice parcial. El actor y el espacio los afirma la aplicación (seguimientos 29, 46).
- **Otros seguimientos:** 62 `kernel.timer.process` y espacio suspendido (los aplica execution-13; seguimiento 44); 63 `timers` sin retención ni purga; 64 el evento llega solo a `internal`.
- **(g) Documentación.** `docs/02-arquitectura/kernel.md` debe decir: en producción nada dispara timers hasta el proceso programador (M4 o antes); falta un proceso periódico en `services/api` que recorra los espacios activos (el ADR de despacho entre espacios del seguimiento 39), llame por espacio a `FireDueTimers` con `model.SystemClock` y el actor `system`, registre `scheduler_runs`, verifique `kernel.timer.process` con `Authorizer.Check` (execution-13) y no se exponga por B3.

## Fuera de alcance
Proceso periódico y `scheduler_runs`, recordatorios previos al vencimiento y `signal_type`, reintentos de timers, evento de reprogramación, `Authorizer.Check` en el disparo (execution-13), pausa por espacio suspendido, retención de timers, cumplimiento tardío, mora e intereses, idempotencia (idempotency-14).
